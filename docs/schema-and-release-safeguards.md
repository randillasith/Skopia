# Schema and release safeguards (proposed operations)

`src/main/resources/schema.sql` is a **fresh-install reference**, not an upgrade script. Existing MySQL/MariaDB databases are upgraded at application startup by `FeatureSchemaMigration`, `BillingSchemaMigration`, and `RefundSchemaMigration` after Hibernate has created/matched tables. Do not run `schema.sql` against production as a migration: `CREATE TABLE IF NOT EXISTS` cannot correct existing columns, indexes or foreign keys. The billing runner replaces restrictive `subscriptions.viewer_id` foreign keys with a reference to `viewers`; feature migration makes `announcements.publish_date` nullable and backfills notifications/refunds; refund migration adds payment currency, refund category/currency/version, refund history, a unique payment constraint and reporting indexes. Refund migration aborts on unknown statuses or duplicate refunds per payment; inspect/resolve those rows before retrying, never delete them blindly. Back up the real database first and rehearse the upgrade against a restored disposable MariaDB 10.11 database. Check `information_schema.key_column_usage`, `columns`, and `statistics` after boot and again after a repeat boot for idempotence. On a disposable MariaDB 10.11 container, the revised fresh schema created 37 tables; starting the packaged app against a database initialized from the previous `schema.sql` reached `Started SkopiaApplication` and produced the expected history table, payment currency, nullable announcement publish date, unique refund index, and `subscriptions.viewer_id -> viewers` FK. Hibernate also warned while trying to add an `id` auto-increment column to the existing `reports` table (which has `report_id` already); this unrelated reference/entity mismatch remains to be resolved before claiming a warning-free full-schema upgrade. The first non-web smoke attempt failed because servlet security needs `HttpSecurity`; the successful attempt used the normal web app and a throwaway auth secret. No production database was used.

## Proposed host-script change — NOT applied to `/opt/skopia/deploy-main.sh`

The host script must be reviewed against its actual revision and backed up before editing. Under its existing deploy flock, before **any** application startup/migration or main push deployment, take and verify a private consistent MariaDB dump using the service EnvironmentFile's actual datasource keys (never log credentials), an uploads snapshot, the EnvironmentFile, previous JAR and receipt; confirm available storage and restore access. A JAR rollback alone does not reverse database migration; rehearse restoring the DB/uploads/old JAR together on isolated infrastructure and retain backups if a deploy fails. Do not overwrite production DB from a test.

Replace a curl-exit-only local health probe with a semantic assertion such as:

```bash
curl --fail --silent --show-error --connect-timeout 5 --max-time 10 \
  http://127.0.0.1:8080/api/health | jq -e '.status == "ok"' >/dev/null
```

Adjust port from the actual service configuration. Perform the same JSON check on the public HTTPS endpoint, verify `/browse` and representative public API behavior, then atomically write the deployed-SHA receipt **only after** all probes succeed. `/api/health` currently returns `{ "status": "ok", "module": "Video Content, Playback & Viewer Interaction" }`: this proves the app responds but does **not** check database readiness; add a DB-aware readiness endpoint and exercise it before treating this as a migration-safe production gate. Test bad JSON, HTTP errors, DB outage and rollback on a disposable clone. No host script or protection rule was changed here.
